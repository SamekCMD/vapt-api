Defaults de cluster e settings efetivos do pool Hyperdrive **não foram provados**; não deduzir timeout efetivo zero desse resultado.

Leitura local confirma `createWorkerServices` usa `createWorkerDatabase(env)` semdiagnostic e os prazos5s/8s/10s/2s só são definidos emdiagnostic:true. Em pg8.23.0 instalado, `getStartupConf` envia statement/lock como parâmetros de startup; `query_timeout` retorna erro de leitura, mas o caminho de query já enviada sempipeline não envia CancelRequest nem destrói automaticamente a conexão. Portanto não aplicar apenas Promise.race/query_timeout e chamar isso de cancelamento SQL. Pool.query remove o cliente em erro; clientes explicitamente adquiridos por transações/Better Auth precisam preservar ownership, rollback/release e não retornar cliente ainda ocupado ao pool.

Referências oficiais conferidas: [Hyperdrive limita statement a60s e conexão inicial a15s](https://developers.cloudflare.com/hyperdrive/platform/limits/); esses limites de plataforma não são os deadlines menores da aplicação. [Pooling é transacional e SET se aplica à query/transação, sendo resetado ao devolver a conexão](https://developers.cloudflare.com/hyperdrive/concepts/connection-pooling/). [Estado de sessão não documentado é incompatível](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/). Não assumir que parâmetros de startup pg são aplicados ao backend nem envolver toda request numa transação só para manterSET.
